# Добавление сцен

## Сценарий и контракт runtime

`Scene` содержит `id`, `chapter`, `title`, `commands`. Ключ в реестре `scenes` совпадает с `id`. Типы команд и состояния описаны JSDoc в `src/engine.js`.

`SceneRunner` получает реестр сцен и runtime:

```js
{
  sceneChanged(scene, state) {},
  async execute(command, signal) {},
  error(error) {},
}
```

`execute` завершается после выполнения действия. Для `vote` возвращает идентификатор выбранного варианта; runtime предварительно ждёт разрешения ведущего продолжить. Проигрыватель записывает результат в `state.flags[command.id]` и самостоятельно обрабатывает `branch`, `goto`, `parallel`.

Пример сцены на существующих механиках:

```js
scene05: {
  id: 'scene05', chapter: '05', title: 'Новая встреча',
  commands: [
    { type: 'location', id: 'street', actors: {
      nikita: { x: 150, y: 355 }, sonya: { x: 660, y: 355 },
    } },
    { type: 'move', actor: 'nikita', path: [[480, 355], [610, 355]], duration: 2000 },
    { type: 'dialogue', actor: 'sonya', text: 'Ну что, готов?' },
    { type: 'goto', target: 'scene04' },
  ],
}
```

Все координаты заданы в логическом мире 960×540, начало сверху слева; координата персонажа обозначает его стопы. Маршрут содержит последовательность точек, скорость распределяется по длинам сегментов. Проходимость и поиск пути отсутствуют: автор задаёт свободный маршрут.

## Параллельные действия и отмена

`parallel` запускает дочерние команды одновременно и ждёт их все. Не помещайте туда диалоги, голосования, заголовки, переписку, смену локации и переходы. Не запускайте одновременно два движения одного персонажа или две анимации одного свойства камеры: такие конфликты автор должен исключать.

Каждый асинхронный обработчик обязан использовать переданный `signal` и часы `GameClock`. Нельзя заменять их неотменяемым `setTimeout`: иначе события старой сцены могут попасть в новое прохождение. Обработчик пользовательского ввода одноразовый; нажатия вне активного ожидания не запоминаются.

Смена локации задаёт полный набор её персонажей и сбрасывает камеру. Переход между сценами сам по себе мир не очищает: это позволяет сценам 01–03 использовать одну аудиторию. `start()` отменяет прежний запуск и создаёт новое состояние, `stop()` отменяет текущую работу.

## Ресурсы и новые механики

Персонажи, имена, цвета, локации, позы, звуки и вложения зарегистрированы в `resources.js`. Спрайты и геометрия локаций рисуются в `world.js`, представления диалога/переписки — в `ui.js`. Для новой декорации добавить запись локации и соответствующее рисование; сценарные команды остаются прежними.

Для нового типа действия добавить JSDoc-контракт, проверку в `validateScenes` и обработчик runtime в `main.js`. Не добавлять проверки вида «если текущая сцена X» в общие компоненты.

## Голосование, задания и прогресс

Текущий `LocalVoting` имеет `start({id, duration}, clock, signal) → Promise<Choice>`, `choose(choice)`, `finish()`, `cancel()` и событие `change`. Состояния: idle, active, awaiting-choice, ready. `remaining` выражен в миллисекундах. `choose` и `finish` нужны локальной панели репетиции; серверный подсчёт должен будет заменить источник результата.

Для сетевого голосования `FirebaseVoting` подставляется вместо локального адаптера. Runtime ждёт подтверждения ведущего перед публикацией результата и переходом к следующей реплике.

Задания задаются командой `activity` с идентификатором из реестра и длительностью в миллисекундах. Ведущий публикует дедлайн в комнате, телефоны самостоятельно ведут свои этапы. Следующую станцию публикует команда `station`, а `key` увеличивает счётчик ключей в `GameState` и публикует следующий пункт маршрута. Для сокращённой версии сценарий может задать `shortText`, `shortTarget` и `shortNextStation` у соответствующих команд.
