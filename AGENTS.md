# Agents.md

## 0. Общий принцип

Агент работает в режиме, определяемом типом запроса пользователя.

Перед выполнением задачи агент обязан:
- определить режим работы
- действовать строго в рамках выбранного режима

---

## 1. Режимы работы агента

Агент работает в одном из трёх режимов:

---

### 1.1. Code Mode (написание кода / рефакторинг)

Включается, если:
- пользователь просит написать код
- пользователь просит изменить или улучшить существующий код
- пользователь просит исправить баг
- пользователь просит провести рефакторинг

Особенности:
- допускаются изменения файлов проекта
- допускаются архитектурные изменения
- результатом является изменённый код

---

### 1.2. Spec Mode (составление спецификации)

Включается, если:
- пользователь просит описать функциональность
- пользователь просит составить спецификацию
- пользователь формулирует задачу без требования писать код

Особенности:
- создаётся документ спецификации
- изменения в коде не производятся
- результат — описание, а не реализация

---

### 1.3. Other Mode (прочее)

Включается, если:
- пользователь задаёт вопрос
- пользователь просит объяснение
- пользователь уточняет детали
- пользователь просит мелкие правки, не являющиеся рефакторингом

Особенности:
- код не изменяется (если явно не требуется)
- нет полноценной итерации разработки

---

## 2. Snapshot Policy

### Основное правило

Snapshot создаётся **ТОЛЬКО в Code Mode**.

---

### Жёсткий запрет

Snapshot **СТРОГО ЗАПРЕЩЁН** в Spec Mode.

---

### Прочие случаи

- В Other Mode snapshot не создаётся
- Пользователь может явно переопределить поведение:
    - "не создавать snapshot" → snapshot не создаётся
    - "создать snapshot" → snapshot создаётся независимо от режима

---

### Полный регламент

Подробные правила описаны в:

`docs/common/iteration-snapshots.md`

Агент обязан следовать этому документу при создании snapshot.

---

## 3. Architecture Docs Policy

Агент обязан поддерживать архитектурную документацию в `docs/architecture/`:

- `docs/architecture/core.md` — только стабильные архитектурные инварианты.
- `docs/architecture/current-state.md` — только фактическое текущее состояние системы.
- `docs/architecture/decisions/*.md` — ADR-lite решения (одно решение = один файл).

### 3.1. Обновление по режимам

- `Code Mode`:
  - обновлять `current-state.md` по фактическим изменениям;
  - фиксировать архитектурные выборы в `decisions/*.md`;
  - обновлять `core.md` только при изменении стабильных инвариантов.
- `Spec Mode`:
  - допускаются спецификации и черновики;
  - snapshot создавать запрещено.
- `Other Mode`:
  - допускаются анализ и объяснения;
  - архитектурные документы не помечаются как изменённые по факту, если код не менялся.

### 3.2. Source Of Truth

Код является источником истины.

Если документация расходится с кодом:
- приоритет у кода;
- документация должна быть обновлена в ближайшей итерации `Code Mode`.

---

## 4. Session Bootstrap (обязательный)

В начале каждой новой сессии агент обязан:

1. Прочитать `AGENTS.md`.
2. Прочитать `docs/common/iteration-snapshots.md`.
3. Прочитать архитектурные документы:
   - `docs/architecture/core.md`
   - `docs/architecture/current-state.md`
   - последние записи в `docs/architecture/decisions/`.
4. Определить режим задачи (`Code/Spec/Other`) и действовать в его рамках.

---

## 5. Алгоритм работы агента

Перед выполнением любой задачи:

1. Определить режим:
    - Code Mode / Spec Mode / Other Mode

2. Выполнить задачу в рамках режима

3. Проверить необходимость snapshot:
    - Code Mode → создать snapshot
    - Spec Mode → НЕ создавать snapshot (запрещено)
    - Other Mode → НЕ создавать snapshot

4. Учитывать явные указания пользователя (если есть)

---

## 6. Приоритеты

При конфликте:

1. Явное указание пользователя
2. Этот документ (agents.md)
3. `docs/common/iteration-snapshots.md`
4. `docs/architecture/*`
5. Остальная документация проекта
